# jwin 인스턴트윈 — 캠페인 단위 당첨확률 + 수량 비례 상품 추첨 + 소진 페이싱

작성일: 2026-10-24

## 1. 의도와 배경

지금 jwin 추첨(`apps/jwin-api/src/services/draw.ts`)은 경품마다 확률을 따로 들고,
tier 오름차순으로 `rand() < prize.winProbability` 를 순차 판정한다. 먼저 걸리는
경품이 당첨이다.

이 구조에는 두 가지 문제가 있다.

**운영자가 확률을 설계할 수 없다.** 경품이 세 개면 확률도 세 개를 각각 정해야 하고,
순차 판정이라 "전체 당첨률"이 입력값에서 바로 보이지 않는다. 합이 1을 넘어도 막지
않고 경고만 띄우는 현재 동작(`prizeProbability.ts`)이 그 증상이다. tier 순서에 따라
앞쪽 경품이 체계적으로 유리해지는 편향도 있다.

**경품이 남는다.** 확률이 고정이라 실제 응모량이 예상보다 적으면 캠페인이 끝나도
재고가 남는다. 남은 경품은 브랜드 입장에서 그대로 손실이고, 이벤트 목적(노출·참여)도
덜 달성된다.

그래서 두 가지를 바꾼다. 확률은 **캠페인 단위 하나**로 올리고, 어떤 상품이 나가는지는
**남은 수량 비례**로 정한다. 그리고 소진 속도가 계획보다 느리면 확률을 **자동으로
끌어올려** 캠페인 종료 시점에 재고가 비도록 민다.

## 2. 목표 / 비목표 / 실패 조건

### 목표

- 운영자는 캠페인당 당첨확률 **숫자 하나**만 설정한다.
- 당첨 시 상품은 남은 수량에 비례해 뽑힌다. A 10개 / B 30개 / C 1개면 10:30:1.
- 응모량을 모르는 상태에서도 캠페인 기간 안에 경품이 소진되도록 확률이 스스로 보정된다.
- 보정은 설정값이 틀려도(과소·과대) 실제 트래픽이 요구하는 수준으로 수렴한다.

### 비목표

- 경품별 개별 확률. 수량 비례로 대체되며, 되살릴 계획 없음.
- tier(등급) 개념. 수량 비례 추첨에서 등급은 추첨에 아무 역할도 하지 않는다.
- 유저별·세그먼트별 확률 차등.
- 응모량 예측 모델. 보정 루프가 사후 피드백으로 처리한다.

### 실패 조건 (동작해도 실패로 본다)

- **미래 재고를 당겨 쓴다.** 보정이 과해져서 캠페인 중반에 경품이 동나고 남은 기간이
  빈 껍데기가 되는 것.
- **추첨이 선착순이 된다.** 확률이 과하게 떠서 구간이 열리자마자 몇 분 안에 당첨이
  확정되는 것. 유저가 "특정 시각에 들어가야 먹는다"를 학습하면 이벤트가 망가진다.
- **보정이 톱니질한다.** 올렸다 내렸다를 반복하며 매 주기 죽은 구간을 버리는 것.

## 3. 핵심 설계

### 3.1 두 단계 추첨

응모 1건이 들어오면:

**1단계 — 당첨 여부.** 캠페인에 설정된 기준 확률 × 보정 배수로 주사위를 한 번 굴린다.
경품이 몇 종류든 판정은 한 번이다.

**2단계 — 상품 결정.** 당첨이면 남은 수량이 있는 경품들에 대해 `remainingQty` 를
가중치로 하는 가중 랜덤을 돌린다.

> A 10 / B 30 / C 1 → 합 41 → A 24.4%, B 73.2%, C 2.4%

**가중치는 `totalQty` 가 아니라 `remainingQty` 다.** 소진된 경품은 가중치 0이 되어
자동으로 후보에서 빠지고, 수량이 많아 빨리 줄어드는 경품은 가중치도 같이 내려간다.
1개짜리 희귀 경품은 초반엔 거의 안 나오지만 다른 재고가 마르면서 상대 가중치가 올라가
결국 나갈 확률이 높아진다. 별도 보정 없이 종류별 소진이 같이 끝나는 방향으로 수렴한다.

### 3.2 누적 스케줄 게이트 (하드 상한)

소진 속도의 하드 상한은 **누적 계획선**으로 건다.

```
소진량 = Σ(totalQty − remainingQty)
계획량 = Σ totalQty × (현재 − campaign.startsAt) ÷ (campaign.endsAt − campaign.startsAt)

소진량 ≥ 계획량  →  확률 판정 없이 낙첨
```

이게 "미래 재고를 당겨 쓴다" 실패 조건(§2)을 막는 가드다. 계획선보다 앞서 나가는 건
절대 불가능하고, **뒤처진 만큼은 언제든 몰아서 나갈 수 있다.** 확률은 계획선 아래에서
"언제" 당첨이 나올지를 정하는 속도 조절값일 뿐이다.

**구간당 상한을 두지 않는 이유.** 초기 설계는 구간마다 정확히 1개로 상한을 뒀는데,
시뮬레이션에서 전 시나리오 최하위로 나왔다. 한 구간에서 당첨이 0건일 확률은 항상 0보다
크고, 상한이 1이면 그 손실을 어디서도 메울 수 없어 장기 평균이 구조적으로 1 미만으로
깔린다. 결과는 후반 몰림과 잔여 재고다.

| 2000응모/일 · 360개/30일 | 소진 | 전반기 소진 |
|---|---|---|
| 구간당 정확히 1개 | 97.7% | 35.3% |
| 누적 스케줄 게이트 | 99.5% | 49.5% |

| 재고 밀집 3000개/30일 | 소진 | 전반기 소진 |
|---|---|---|
| 구간당 정확히 1개 | 87.3% | 26.0% |
| 누적 스케줄 게이트 | 99.3% | 44.5% |

상한을 아예 없애는 안도 정상 설정에서는 비슷하게 좋지만(99.9%), 기준 확률이 과대
설정된 경우 전반기에 전량 소진되어 실패 조건 1에 정면으로 걸린다.

게이트는 `Prize.totalQty` 와 `remainingQty` 만으로 계산된다. **추가 상태 필드가 필요
없다.**

### 3.3 구간(window) — 보정 배수의 갱신 주기

구간은 하드 상한과 무관하며, 오직 **보정 배수 M 을 언제 갱신할지**를 정한다.

```
구간 길이 L = max(2시간, (캠페인 종료 시각 − 구간 시작) ÷ 남은 총 재고)
구간 계획량 = max(1, round(L ÷ 자연 구간 길이))
```

- 30일 × 24h ÷ 360개 = 2시간 → `L` = **2시간**, 계획량 1
- 10일 지나 260개 남음 → 1시간 51분 → 하한에 걸려 `L` = **2시간**, 계획량 1
- 재고 3000개 / 30일 → 자연 14.4분 → `L` = **2시간**, 계획량 **8**
- 재고 10개 / 남은 30일 → `L` = **72시간**, 계획량 1

**2시간 하한을 두는 이유.** 재고가 밀집한 캠페인은 자연 구간이 14분까지 짧아진다.
14분마다 M 을 ×1.5 / ×0.5 로 흔들면 표본이 너무 작아 노이즈만 증폭된다. 하한을 걸면
구간이 넓어지는 대신 계획량이 1보다 커지고, M 은 안정적인 표본 위에서 갱신된다.

**구간은 날짜 경계를 무시하고 캠페인 시작 시각부터 연속으로 흐른다.** 자정 개념이
없다. 일별 집계가 필요하면 `Winner.createdAt` 으로 사후 조회하면 된다.

### 3.4 보정 배수

```
적용 확률 = 기준 확률 × M
```

구간이 끝날 때 M 을 갱신한다.

| 직전 구간 | 갱신 |
|---|---|
| 당첨 수 < 구간 계획량 (응모는 있었음) | M ← M × 1.5 |
| 당첨 수 ≥ 구간 계획량 | M ← M × 0.5 |
| **응모가 0건이었음** | **M 유지** |

**응모 0건 구간을 미달로 치지 않는 이유.** 확률을 올려도 응모가 없으면 아무 일도 일어나지
않는다. 미달로 치면 응모 불가 구간(당일 포스트 미발행 등)에 M 이 ×1.5 로 복리 누적되고,
응모가 재개되는 순간 과열 상태로 시작해 선착순이 된다(실패 조건 2). 2시간 구간에서 하루를
쉬면 1.5^12 ≈ 130배다. 상한(§3.5)이 폭주 자체는 막지만, 거기서 ×0.5 로 기준까지 내려오는
데 7구간이 걸려 과열이 길게 끌린다. 응모 0건은 "느리다"는 신호가 아니라 **정보가 없다**는
신호이므로 M 을 건드리지 않는다.

기준 0.5% 기준 진행 예:

| 구간 | 직전 결과 | M | 적용 확률 |
|---|---|---|---|
| 1 | — | 1.0 | 0.5% |
| 2 | 미달 | 1.5 | 0.75% |
| 3 | 미달 | 2.25 | 1.125% |
| 4 | 미달 | 3.375 | 1.6875% |
| 5 | 채움 | 1.688 | 0.844% |
| 6 | 채움 | 1.0 (하한) | 0.5% |

**올릴 때 ×1.5, 내릴 때 ×0.5 로 비대칭인 이유.** 확률이 과하게 뜬 상태를 오래 끌면
구간이 열리자마자 당첨이 확정되어 선착순처럼 보인다(실패 조건 2). 올라갈 때는
조심스럽게, 내려올 때는 빠르게.

**완전 리셋이 아니라 절반 감소인 이유.** 기준 확률은 운영자의 추측값이고, 실제 응모량은
사전에 알 수 없다(참고 플랫폼 기준 2천 건/일 추정). 실제 적정 확률이 1%인데 기준이
0.5%로 잡혔다고 하자. 완전 리셋이면 "몇 구간 비움 → 따라잡음 → 0.5%로 복귀 → 또 비움"을
캠페인 내내 반복하며 매 주기 죽은 구간을 버린다(실패 조건 3). 절반 감소는 실제 트래픽이
요구하는 배수 근처에 눌러앉는다. 즉 **틀린 초기값을 스스로 교정하는 쪽**이다.

### 3.5 M 의 범위

```
M ∈ [1.0, P_MAX / 기준 확률]      P_MAX = 0.5
```

**하한 1.0.** 기준 확률이 바닥이고 보정은 위로만 간다. 설정 확률은 운영자와 브랜드 사이의
약속 같은 숫자여서, 시스템이 임의로 낮추면 설명이 안 된다. 높아지는 건 유저에게 유리한
방향이라 문제가 없다. 기준이 과하게 높게 잡힌 경우(5%를 넣었는데 0.6%가 적정)에도 §3.2
누적 게이트가 조기 소진을 막으므로 — 시뮬레이션에서 전반기 소진 50.0% 유지 — 피해는
"계획선이 열리는 순간 선착순" 한 가지로 제한된다.

**상한은 적용 확률 50% 에서 역산한다.** 적용 확률이 아니라 M 자체를 clamp 해야 한다.
M 을 무한정 올리고 적용 확률만 잘라내면, 트래픽이 돌아왔을 때 거대해진 M 을 ×0.5 로
여러 번 내려야 해서 과열 상태가 오래 간다.

## 4. 데이터 모델 변경

### 추가 — `BrandCampaign`

| 필드 | 타입 | 설명 |
|---|---|---|
| `winProbability` | `Float` | 기준 당첨확률 (0~1). 운영자가 설정 |
| `paceMultiplier` | `Float @default(1)` | 보정 배수 M |
| `windowStartedAt` | `DateTime?` | 현재 구간 시작 시각. null 이면 캠페인 `startsAt` 으로 초기화 |
| `windowWinCount` | `Int @default(0)` | 현재 구간 당첨 수. 구간 계획량과 비교해 M 을 갱신 |
| `windowEntryCount` | `Int @default(0)` | 현재 구간 응모 수. 0이면 M 을 갱신하지 않는다 (§3.4) |

이 네 필드는 전부 **보정 배수 M 을 위한 것**이다. 하드 상한(§3.2)은 기존
`Prize.totalQty` / `remainingQty` 만으로 계산되므로 상태를 추가하지 않는다.

구간 상태를 별도 테이블로 빼지 않는다. 구간은 참여(BrandCampaign) 단위로 하나뿐이고
이력이 필요하면 `Winner.createdAt` 으로 재구성된다.

### 삭제

| 대상 | 사유 |
|---|---|
| `Prize.winProbability` | 캠페인 단위로 승격 |
| `Prize.tier` | 수량 비례 추첨에서 역할 없음 |
| `BrandCampaign.dailyWinCap` | 누적 스케줄 게이트가 상한 역할을 완전히 대체. 둘 다 살아 있으면 캡 때문에 페이싱이 못 따라가 재고가 영영 안 빠지는 조합이 생긴다. 값이 설정된 운영 캠페인 없음이 확인되어 컬럼을 그대로 드롭한다 |

### 마이그레이션

- `BrandCampaign.winProbability` 백필: 해당 캠페인 경품들의 `winProbability` **합계**를
  `[0, 1]` 로 clamp. 순차 판정의 전체 당첨률에 가장 가까운 값이다.
- `paceMultiplier = 1`, 카운터 0, `windowStartedAt = NULL` 로 시작.
  진행 중인 캠페인은 다음 응모 때 현재 시각이 아니라 `campaign.startsAt` 부터 구간을
  계산하므로, 경과 구간만큼 M 이 한 번에 치솟을 수 있다. **마이그레이션에서 진행 중인
  (`status = ACTIVE`) 캠페인은 `windowStartedAt` 을 마이그레이션 실행 시각으로 채운다.**

## 5. 추첨 흐름

`draw()` 의 tier 순차 루프를 아래로 교체한다. 선행 검증(ACTIVE 여부, 기간, 당일 포스트
존재, 응모 1일 1회 유니크 제약)은 그대로 둔다.

1. **구간 롤포워드.** `L` 과 구간 계획량을 계산하고 `windowStartedAt` 부터 몇 구간이
   지났는지 센다.
   - 0구간: 현재 구간 유지.
   - k구간 경과: 첫 구간만 갱신 대상이다 — `windowEntryCount = 0` 이면 M 유지,
     아니면 `windowWinCount ≥ 구간 계획량` 여부에 따라 ×0.5 또는 ×1.5. 건너뛴 나머지
     k−1 구간은 응모가 0건이었다는 뜻이므로(응모가 있었다면 그때 롤포워드가 돌았다)
     **M 을 건드리지 않는다.** `windowStartedAt += k × L`, 카운터 둘 다 0으로.
   - M 을 §3.5 범위로 clamp.
2. **응모 집계.** `windowEntryCount += 1`.
3. **누적 스케줄 게이트(§3.2).** 소진량 ≥ 계획량이면 낙첨 확정.
4. **당첨 판정.** `rng() < winProbability × M` 이 아니면 낙첨.
5. **상품 선택.** `remainingQty > 0` 인 경품에 대해 수량 가중 랜덤.
6. **원자적 차감.** 선택된 경품에 `UPDATE ... WHERE id = ? AND remainingQty > 0`.
   실패하면(동시 응모로 소진) 그 경품을 후보에서 빼고 5로 돌아간다. 후보가 비면 낙첨.
7. **확정.** `Entry(WIN_PENDING)` + `Winner` 생성, `windowWinCount += 1`.
   Entry 유니크 제약 충돌 시 기존대로 차감을 롤백한다.

**미이행 당첨자.** 현행 정책대로 WIN_PENDING 이 팔로우·리포스트 미이행으로 끝나도 재고를
회수하지 않는다. 페이싱 관점에서도 "나간 것"으로 보는 게 맞다 — 재고가 이미 차감되었으므로
`L` 계산에서 자동으로 빠진다. 변경 없음.

롤포워드는 `L` 을 현재 값으로 고정해 계산한다. 엄밀히는 구간마다 `L` 이 조금씩 달라지지만,
롤포워드가 여러 구간에 걸치는 상황은 당첨이 없었다는 뜻이고 그때는 재고가 줄지 않아 `L`
변화가 미미하다. 구현 시 `ponytail:` 주석으로 이 근사와 한계를 남긴다.

**경계 가드.** 남은 재고 0, 남은 시간 ≤ 0 이면 `L` 계산 없이 낙첨.

## 6. 어드민 변경

### 기본 탭 (`BrandCampaignBasicTab`)
- `dailyWinCap` 입력란 제거.
- **당첨확률(%)** 입력란 추가. 저장은 0~1, 표시는 퍼센트. **입력 상한은 50%** — P_MAX 와
  같은 값이다. 기준 확률이 P_MAX 를 넘으면 M 의 유효 범위 `[1, P_MAX/기준]` 이 빈 구간이
  되어 clamp 가 모순된다. 서버 zod 스키마에서도 같은 상한을 건다.
- 활성화 체크리스트(`activationChecklist`)에 "당첨확률 설정됨(> 0)" 항목 추가. 0이면
  당첨이 한 건도 나가지 않으므로 SETUP → ACTIVE 전환을 막는다.

### 경품 탭 (`PrizeTab`, `PrizeAddDialog`, `PrizeEditDialog`)
- `tier`, `winProbability` 입력 필드와 컬럼 제거.
- **수량 비례 당첨 비율** 컬럼 추가 — `remainingQty / 전체 남은 재고` 를 퍼센트로 표시.
  운영자가 "이 경품이 전체 당첨 중 몇 %를 차지하는지"를 바로 본다.
- 목록 정렬은 `tier` 대신 `createdAt`.

### 공유 로직 (`prizeProbability.ts`)
- `probabilitySum`, `isProbabilityOverflow` 삭제. 경품별 확률이 없으므로 합계 경고가
  의미를 잃는다.
- `formatProbabilityPercent` 유지.

### i18n
신규/변경 문자열은 `i18n/admin/messages.ts` 에 ko/en/ja 세 언어 모두 추가하고 `useT()` 로
사용한다. 삭제되는 키(`jwin.prize.field.tier`, `jwin.basic.dailyWinCap` 등)도 같이 정리한다.

## 7. 설계자가 정한 것

- **P_MAX = 0.5.** 적용 확률 상한이자 기준 확률 입력 상한. 운영 데이터가 쌓이면 조정한다.
- **응모 0건 구간은 M 을 갱신하지 않는다** (§3.4).
- **활성화 체크리스트에 당첨확률 > 0 항목 추가** (§6).

### 구현자에게 맡기는 것

- 가중 랜덤 구현 방식(누적합 스캔으로 충분 — 캠페인당 경품 수는 한 자릿수).

  판단한다.

## 8. 검증

프레임워크 없이 `assert` 기반 단위 테스트 하나(`drawPacing.test.ts`)를 남긴다. 시드
고정 rng 로 다음을 확인한다.

- **수량 비례 분포.** A 10 / B 30 / C 1 로 충분히 반복해 10:30:1 에 수렴.
- **소진 경품 제외.** `remainingQty = 0` 인 경품이 절대 선택되지 않음.
- **M 상승.** 구간 3개 연속 미달 → M = 3.375.
- **M 하강과 하한.** 계획량 충족 반복 시 ×0.5 로 내려가 1.0 에서 멈춤.
- **M 상한.** 기준 확률 × M 이 P_MAX 를 넘지 않음.
- **누적 게이트.** 소진량이 계획량에 도달하면 확률 100%여도 추가 당첨이 없음.
- **게이트 이월.** 계획선보다 2개 뒤처진 상태에서 연속 당첨 2건이 허용되고 3건째는 막힘.
- **응모 0건 구간.** 응모 없이 여러 구간을 건너뛰어도 M 이 변하지 않음.
- **구간 길이 하한.** 재고 3000개 / 30일에서 `L` 이 2시간, 계획량이 8로 계산됨.

페이싱 전체의 수렴은 단위 테스트로 잡기 어렵다. 설계 근거가 된 시뮬레이션
(`scratchpad/sim.py` 에서 작성, 저장소에 포함하지 않음)의 결과를 §3.2 표에 남겨두었고,
상수(1.5 / 0.5 / 2시간 / P_MAX)를 바꿀 일이 생기면 같은 방식으로 재검증한다.
- **구간 롤포워드.** 구간 경계를 넘으면 카운터가 리셋되고 M 이 한 번만 갱신됨.
